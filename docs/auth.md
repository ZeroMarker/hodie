# 认证与账号

2026-11-25

应用用 Auth.js 处理登录和会话。本文记录当前实现、设计取舍,以及 2026-11-25 对 Clerk 的评估结论。产品进度见 [开发计划](plan.md)。

## 当前实现

代码在 `web/modules/auth/`,登录页在 `web/app/login/`。

- **框架**:Auth.js v5 + Drizzle Adapter,会话存数据库(`sessions` 表),有效期 60 天,可随时在服务端吊销。
- **已知风险**:依赖 `next-auth` 5.0.0-beta.32;目前线上稳定,但升级大版本时要回归登录、会话和退出,预留验证时间。
- **邮箱魔法链接**:经 Resend 发信,链接 24 小时内有效;生产环境未配置 `AUTH_RESEND_KEY` 时直接报错,本地未配置时把链接打印到终端。发件域名 `20070809.xyz` 已确认送达(2026-10-21)。
- **Google 登录**:代码已就绪,配置 `AUTH_GOOGLE_ID` 和 `AUTH_GOOGLE_SECRET` 后自动出现在登录页;回调地址为 `/api/auth/callback/google`。
- **数据表**:`users`、`accounts`、`sessions`、`verification_tokens` 四张 Auth.js 标准表,迁移见 `web/db/migrations/0001_auth.sql`。
- **取用户**:页面和 Server Action 统一调用 `requireUserId()` 或 `currentUserId()`,不接受客户端传入的 `user_id`;未登录时 `requireUserId()` 跳转 `/login`。

认证只管「是谁」,学习数据仍以 `app.users.id` 为业务主键。`profiles`、`cards`、`review_logs` 等表都引用这个 id。

## 为什么用 Auth.js

- **需求简单**:只需要邮箱和 Google 两种登录,不需要组织、多租户、企业 SSO。
- **数据可控**:用户、会话和账号数据都在自己的 `app` schema,和删除、导出、统计放在一起处理。
- **成本低**:没有按 MAU 计费的认证服务,邮件成本由 Resend 免费额度覆盖。
- **国内可达**:登录页和认证接口与应用同域,不额外依赖一个境外托管的前端域名。
- **实现量小**:接入代码一百多行,已在生产验证过注册、登录、会话和退出。

## Clerk 评估(2026-11-25)

**结论:暂不接入。** 现有认证没有阻碍当前产品目标的功能缺口,换 Clerk 的收益主要是托管 UI、MFA/Passkey、用户管理后台和更多社交登录,这些在当前阶段都用不到。

主要代价:

1. **业务主键迁移**:Clerk 用户 id 是 `user_...` 格式,而现有学习数据全部以内部 UUID 为 `user_id`。要保留历史数据,得额外维护一层 id 映射,并在首次登录时同步用户。
2. **新的外部依赖**:前端需要加载 Clerk 的托管域名,对大陆用户的延迟和可达性多一个变量;数据也多一个境外处理方,阶段 4 的隐私合规要相应增加。
3. **成本模型变化**:从接近零的边际成本变成按 MAU 计价,用户增长会直接带来认证费用。
4. **迁移工作量**:除了换 SDK,还要重做登录态、webhook 同步、账号删除、离线场景验证和端到端测试,对现有用户没有可感知的新功能。

重新评估的触发条件:

- 需要 MFA、Passkey、企业 SSO 或多租户,自己实现成本明显高于订阅费。
- 认证层频繁出安全问题或维护成为明显负担。
- 需要给运营或客服一个用户管理后台。
- 用户主要在境外,国内访问不再是约束。
